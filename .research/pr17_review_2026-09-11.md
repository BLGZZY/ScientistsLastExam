## 1. 当前可复现问题

### P1：允许扩预算恢复，却把正常续跑的结果判为不可验证（已修）

- 原因：`sle/algorithms/evolve.py:449-456` 把本次调用的预算写进每个新 request；
  `:581-588` 允许已有 checkpoint 继续更大的预算。
  `sle/run_verification.py:308-317` 却要求所有历史 request 的 `proposal_budget` 等于最终 summary 的预算。
- 确定性复现：mock evaluator、FakeLLM，在同一目录完成 `budget=0` 后执行 `resume=True,budget=1`。
  首次 `verify_run` 返回 `True`；续跑成功并得到 2 次逻辑 oracle 调用，但验证报
  `ValueError: evaluation receipt proposal_budget differs from manifest`。
  即正常支持的调用会消耗新提案与评测，然后失去报告准入资格。
- 已提交 `520b9f7`：保留每个旧 request/receipt 的原始字节和 hash；校验分配额是非布尔整数，
  满足 `step <= allocation <= final_budget`，并按 step 非递减。外部 `expected_budget` 仍必须匹配最终预算。
  producer 的 resume 也先检查旧 request，禁止缩小已承诺预算。
  尚无 checkpoint 的 baseline 必须先按原预算恢复，避免改变 request ID 再评测一次；
  已抽样的 pending proposal 仍受原 prompt 的 hash 校验约束。
- 验收：正常提案和 no-code 提案两种 `0 -> 1` 续跑均可验证；原 receipt 不变；
  外部预算不匹配、非法/递减分配额仍拒绝；baseline crash 后扩容被拒，原预算恢复复用 receipt，评测器调用数为 0。
- 修复后位置：`sle/evaluation_ledger.py:79`，`sle/algorithms/evolve.py:443`，
  `sle/run_verification.py:325`；回归在 `tests/test_protocol.py`、`tests/test_run_verification.py`。

此规则允许同一运行的延续；它没有把延续后的结果等同于从第一步便获知更大预算的独立实验。
正式对照仍要由 campaign 合同明确是否允许续跑，不能混合两种实验条件。

### P1：验证器没有核对 manifest 与 receipt 的评测时限（已修）

- 原因：producer 在 `sle/algorithms/evolve.py:415` 写入
  `protocol.evaluator_timeout_seconds`，并在每个评测 request 中写入同一字段；
  `sle/run_verification.py:308-355` 未比较这个已被 request hash 绑定的资源约束。
- 复现：完成 `timeout_s=20,budget=0` 的正常 mocked run，只将 manifest 的
  `protocol.evaluator_timeout_seconds` 改为 `200`，原 request/receipt 保持 20，`verify_run` 仍返回 `True`。
  这是验证器漏查已有字段之间的不一致，不是要求本地 hash 链对抗恶意可信操作员。
- 已提交 `752ba6d`：要求 manifest 的评测时限是有限正数，逐个 receipt 的 request 必须具有同一数值；
  不接受 bool、字符串、缺失值、零或负数。原实验文件不补写、不改 hash。
- 验收：改 manifest 和提供绑定到不同 timeout 的 receipt 均拒绝；现有真实 producer 路径及 family promotion fixture 通过。
  修复后位置：`sle/run_verification.py:207`、`:329`。

### P1：trajectory 的时间仍可与 durable receipt 不一致（已复现，未修）

- 位置：`sle/run_verification.py:201-203` 仅从 trajectory 重建 summary；
  `:356-362` 核对计数和分数，却不核对 receipt 的 `evaluation_wall_seconds`。
  `:381-385` 又使用 trajectory 的累计时间判断 cutoff。
- 确定性复现：给测试 fixture 的 `EvaluationLedger.evaluate_once` 注入 `[0.0,2.0]` 时钟，产生耗时 2 秒的正常 baseline receipt；
  把唯一 trajectory event 的 `wall_seconds`、`cumulative_wall_seconds` 改成 0，按 `summarize_trajectory` 重建 summary，
  receipt 和 ledger snapshot 均不改变。原 head 与两项修复后的 `752ba6d` 都返回：

  ```text
  receipt_evaluation_wall_seconds: 2.0
  trajectory_cumulative_wall_seconds: 0.0
  zero_time_run_verified: True
  ```

- 意义：验证器目前不能据此认证 active-wall 的内部一致性。这也不能通过给时间字段重新算 summary 来恢复。
  此处没有声称能伪造新的科学 oracle 结果；缺口是可信记录间矛盾未被拒绝。
- 建议最小修复：baseline 的 active wall 必须与其被消费的 receipt 耗时一致；
  有代码的 proposal 至少核验 `proposal_published_wall_seconds + receipt.evaluation_wall_seconds`
  与 event 的累计时间、前缀时间之间的关系，并复核恢复时 receipt 被重用的时间语义。
  不要简单要求 trajectory active wall 等于 ledger 全部 physical attempt 时间：失败重试与成功逻辑评测的账本含义不同。
- 验收：上述 2 秒/0 秒矛盾必须失败；无故障、provider 重试、评测失败恢复、receipt 已提交但 trajectory 未提交、
  no-code、late result、fixed-grid sentinel 均需通过各自时钟合同回归。

## 4. Family/lifetime credit：目前是 opt-in 协议，尚无真实任务证据

当前 `benchmarks/**/frontier_eval/wave.yaml` 数量为 **0**。已有 family 回归是 synthetic fixture，
不能据此声称 optimization/discovery 的持续科学研究能力已经得到验证。

- 固定 wave 的 `combined_score` 和跨 wave 的累计 frontier credit 是两种量。
  `sle/frontier.py:563-641` 的 optimization credit 为越过 minimum delta 后的加权增量；
  discovery credit 为同一 family/namespace 中首个 canonical claim 的固定权重。
- `docs/frontier_families.md:105-121` 已明确 discovery credit 不含 FDR/refusal 处罚、没有通用 credit cap。
  这是待任务设计决定的测量政策，不是可任意声称“积分越高整体科研越好”的依据。
  `minimum_delta` 与 promotion 顺序会影响哪些中间改进获准入；比较时还需冻结顺序、cell 权重与允许的研究次数。
- 原 head 已有 baseline/valid blanket abstention 不得产出 frontier records 的 contribution gate，
  `sle/frontier.py:800-810` 已封闭未验证的公开 `record` 路径，
  `:991-1064` 的 promotion 验证当前 task/runtime 与 receipt，并要求 ledger 位于 run 之外。
  不重复旧 review 中“任意公开 record 即可得分”的已修问题。
- `sle/frontier.py:350-363` 的 family audit 已拒绝 literal clone；语义等价但编码不同的伪创新仍需要任务审查，
  最新文档 `:143-154` 已披露。通用 ledger 不可能替代 oracle 的证据谓词。
- 本地 hash chain 的 fsync/idempotency 不等于独立签名；最新文档已要求可信操作员选定共享 ledger 并外部锚定 head。
  正式发布前应冻结 campaign 的 canonical ledger、promotion policy、外部 head，避免按 run 私建“全局累计量”。

最小科学验收是至少各有一个 optimization 与 discovery 的真实 opt-in family，两次 frozen wave，
baseline/cheap probe 无新 credit，重复 claim 为 0，wave 变更不复用旧 novel credit，
独立复测/held-out confirmation 支持新增记录；discovery 三轴与 credit 分列。
在此之前 family 可作为实验接口，但不宜用于正式榜单升档。

## 5. 最小依赖拆分

1. **保留已集成 runtime safety 的独立基线。** 不从 PR #17 恢复旧 85 wrapper、旧 metrics sidecar、旧 infrastructure error 传播。
   `8695763` 的公共过滤、0700 私有目录、failure marker、sanitized feedback 和 #69/#37 祖先均应保留。
2. **Runtime profile/identity 独立 PR。** 成组移植 `oracle_package_pins`、`runtime_identity`、ABI/package mount、
   `evaluate`/`trusted_driver` 参数与 envelope；Linux 测试通过后再启用新 run 格式。
   不能只移植 driver 的 required flag 而漏掉全部调用方。
3. **Run verification/格式升级独立 PR。** 合入 `520b9f7`、`752ba6d` 的两项修复，补齐时钟一致性，
   明确新旧格式、外部预算合同及 completion 条件。`early termination` 与非 greedy 暂不能通过新版验证是现有范围限制，
   不应在报表里伪装成新的科学无效样本。
4. **Family ledger 独立 opt-in PR。** 只依赖一个稳定的 verified-receipt 接口，加入 metadata/wave/审核逻辑；
   没有 family metadata 的任务行为保持普通任务。真实 family admission 随单独科学证据提交。
5. **报告和历史证据独立 PR。** PR #17 内的多份 calibration/report 改动应适配当前共享 trajectory/report 接口，
   避免覆盖本轮 #66/reporting 修复。既有证据仍按原 revision 检查，不把 runtime hash 重绑当作重跑。

这些是依赖顺序，不是建议把 PR 中间所有 evidence 文档无差别 cherry-pick。
当前 review 分支以整个 PR #17 为祖先：**root 当前 runtime 集成不要 merge 该分支**；
后续处理 PR #17 时选择两项独立修复 commit。审查文档也可单独 cherry-pick。
